# Learnings — what this project does and does not prove

This is an honest note, not a claim of live Maximo experience. It is a self-directed
project using synthetic data. As of 2026-11-22, live instance access was unavailable, so the
project runs in **file mode** and the REST client/loader are proven only against a mock.

## What is proven now (offline / file mode)

- A realistic BESS asset hierarchy can be generated deterministically: 77 locations and 359
  assets across site → block → container → rack → module, with the equipment families a
  battery site actually has (PCS, MV transformer, HVAC, fire detection/suppression, BMS,
  SCADA, switchgear).
- Data quality can be made **testable**: injecting a known, counted defect set and comparing
  findings as a multiset gives exact recall/precision, not a subjective “looks better”.
- Clean data produces zero findings. That is a stronger check on the rules than finding the
  planted defects, because it catches over-broad rules.
- The same check code can drive the report and the CSV fallback without duplication, because
  the boundary is a `Repository` rather than HTTP.
- Maximo-format import CSVs can be read back by the same checker: 44/44 defects, no false
  positives. That is the fallback workflow, end to end.
- Idempotent loading is a property you can test against a mock: lookup by natural key,
  dependency order, and a second run that creates nothing.
- Excel formatting is part of the deliverable: frozen headers, autofilters, dates and
  percentages. A report a manager cannot scan is not a report.

## What is deliberately unverified

Everything in the Maximo mapping: the auth header, object-structure names, paging shape,
PATCH behaviour, PM last-completed and labour columns, problem/failure columns, status
domains, parent/cycle validation, and whether a trial enforces required fields. These are
isolated in [`src/mxbess/mapping.py`](../src/mxbess/mapping.py) and listed in
[`instance-notes.md`](instance-notes.md).

The mock proves the client and loader code paths. It does not prove the live API. File mode
runs on CSVs generated by this project, not on an export from a real Maximo instance.

## Questions to answer if access becomes available

- Which of the injected defects can the API reject (A04 required fields, A06 parent/cycle,
  direct COMP/CLOSE transitions), and what is the right workaround?
- How does Maximo represent actual labour hours on the WO versus LABTRANS, and which one
  should the W02 check use live?
- Does the instance's PM model store last-completed in LASTCOMPDATE, and is FREQUNIT=DAYS
  accepted?
- How long does the full load actually take with paging and validation? The five-minute
  criterion is a target, not a measured fact.
- What does the Maximo UI teach that the documentation did not? That answer is the one
  worth using in an interview, and it is not in this repository.

## Interview framing (honest version)

- CV line, project section (safe now, file mode):
  *Maximo BESS data-quality project: generated a synthetic battery-storage asset hierarchy,
  PMs and work orders; produced Maximo import CSVs, 14 automated data-quality checks and an
  Excel PM/backlog report.*
- Do **not** use “loaded via REST API” or imply live Maximo experience unless a live run
  actually happens. The client and loader are mock-tested only.
- Label it a self-directed project using synthetic data; it is not employment and not a
  year of Maximo experience.
- The interesting parts are the rules, the definitions (what “PM compliance” counts), and
  the guardrails that would stop the defects recurring — not the scripts.
- Interview points to prepare: what a duplicate or orphaned asset costs a maintenance team;
  how to stop it recurring; how PM compliance is calculated and why it can mislead; which
  parts are file-mode simulation and which would need a live instance.
